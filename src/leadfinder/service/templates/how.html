How it works

Code finds and ranks the practices; a person asks for each email and approves it

Submitted visits pass an intent gate before practice matching; the existing demo leads show the downstream scoring and review steps · nothing is sent from here1

Workflow graph · active nodes, agents, and the planned research node

Submitted visits · intent gate before practice lookup

The deterministic gate analyzes visit behavior first. It is not the conversion scorer: it decides whether the visit has enough intent to proceed. No local practice match or lead score happens before this gate.

Qualified and confidently identified
The gate returns research. The current demo then attempts a unique exact local practice-name match, narrowed by location when supplied; only after a match does it attach derived visit categories and create or rescore the lead. This is a local synthetic-record lookup, not external research.
Qualified, identity uncertain
The gate returns human_review. No practice-specific lookup or scoring happens until an SDR verifies an existing local practice; then the same visit-attachment and lead-scoring handoff runs.
Low intent or not marked scrubbed
The gate returns stop. The app does not match a practice or score a lead for that visit.
After the handoff
The trained model's conversion chance and the points-table score rank the identified practice. They are separate from the gate's intent decision.

A logged-in staff client submits visit data to POST /api/visit-analysis; the intent gate runs before any practice matching. If behavior qualifies but identity is missing or uncertain, the gate stores a review case in SQLite. An SDR can open Visit review, verify it against an existing practice, or close it with a reason. The decision records who acted and when.

Before submission
The caller must allowlist and scrub the data. The API trusts `patient_data_stripped`; it is not a scrubber. Unsanitized submissions stop and are not persisted.
After identity verification
The case's derived visit categories are attached to the selected local practice, then the shared handoff creates or rescores its lead. An automatically identified, intent-qualified visit uses the same routine after a unique exact local name match, narrowed by location when supplied. This demo lookup is synthetic and does not launch external research or create a new practice.
Unresolved after review
Close the case with a reason. No practice-specific research runs.

Scoring · two scorers on the same facts

Every lead gets two scores, and both show their working on the lead's page.

The trained model
{% if model %}A {{ model.kind }} ({{ model.version }}) that gives each lead a chance of converting. It ranks the list. Each fact about the practice moves the chance up or down by an amount that is shown, and the amounts add up to the prediction exactly.{% else %}Not trained yet; the points table ranks the list.{% endif %}
The points table
Set by hand: so many points for the specialty, the size, the EHR and each page visited, capped at 100. It is kept beside the model so a rep can see where the two disagree.
What both see
Specialty, number of providers, EHR, the pages visited and whether a visit was in the last 7 days. Nothing else.
What the model learned from
A simulated history, because there are no real outcomes yet3. The benchmark and every weight.
Which version is live
{% if model %}{{ model.version }}. A new version is fitted each simulated month and marked against the live one on a scorecard of four measures; it goes live only if it wins the card. Every version side by side.{% else %}None yet.{% endif %}

Writing · only when a person asks{% call note('write-note', 'Why the email waits for a button') %}An email nobody asked for is words nobody has read. Writing on request means every email on a lead's page is one a person wanted, and a lead that is going to be rejected never gets one.{% endcall %}

When
When the SDR presses “{{ 'Have Claude write the email' if writer.is_model else 'Write the email' }}” on a lead's page. Until then the lead has no email. The call brief starts as a template{{ ' and Claude rewrites it on request' if writer.is_model else '' }}.
Who writes
{% if writer.is_model %}Claude, the language model. Without a credential the same button fills a template.{% else %}A template, because no Claude credential is set. Set ANTHROPIC_API_KEY and restart, and Claude writes it.{% endif %}
What the writer is given
The practice's name, specialty, number of providers, city, state and EHR, the contact's name, the pages visited, and the score's reasons.
What it is never given
The contact's email address, the NPI, or anything about patients. None of that is needed to write the words.
What code checks
No patient information; no claim the seller cannot back, such as a guarantee or “HIPAA certified”; no EHR and no number of providers that is not on the practice's record. Words that fail are not kept, and the page says why.
What code adds
The footer with the postal address and the way to opt out, which CAN-SPAM requires. The model does not write it.

The decision · a person's, and logged

Approve
The SDR may edit the subject and the body first. What is approved is what they left on the page, and the log keeps that it was edited. The guardrail runs on those words before the approval lands: no patient information, no claim the seller cannot back, the footer still in place.
Reject
With one of {{ reject_reasons|length }} reasons ({{ reject_reasons.values()|join('; ') }}) and an optional note. A lead can be rejected without ever having an email written.
Two people, one lead
If someone else decides a lead while it is open on your screen, your decision is refused and the page shows theirs.
The audit log
Every approval and rejection: who, when, the chance and the points that were on screen, whether the email was edited, and who wrote it. The sales manager reads it{% if can.view_audit %} here{% endif %}.
Who sees what
SDRs see the leads and decide them. The sales manager sees all of that and the audit log.
